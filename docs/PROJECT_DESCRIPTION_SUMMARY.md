# DeadDrop: Brief Technical Overview

DeadDrop is a mutually authenticated, encrypted communication system for two paired Raspberry Pi 5 field terminals, built to exchange messages without relying on any third party message server. Each device is self contained, with a touchscreen interface, hardware status indicators, and text to speech for incoming messages.

The two devices connect over a private WireGuard based mesh network (Tailscale), with a self hosted DERP relay handling the small share of connections that cannot establish a direct peer to peer path. On top of that network, each device performs a mutual TLS 1.3 handshake using wolfSSL, with certificates issued by a private, purpose built certificate authority whose private key has since been moved to offline storage. A local revocation list is checked inside the same TLS verification callback that performs chain validation, and this rejection path has been confirmed with a live test using a genuinely valid but revoked certificate.

Above the TLS session, a custom application protocol handles message framing, HMAC authentication derived from the TLS session's own exported keying material, and strict sequence number enforcement to prevent replay. This protocol has been fuzz tested with over one million randomized and structurally mutated inputs under AddressSanitizer and UndefinedBehaviorSanitizer with no crashes or sanitizer findings.

Each device's storage is fully encrypted with LUKS2, with the decryption key derived from a secret held in the Raspberry Pi 5's own one time programmable fuse memory rather than stored in any file or backup. This binds the encrypted storage to the specific physical chip it was provisioned on. The property was verified directly: a provisioned card was physically moved to a different, otherwise identical device, which derived a different key from its own unburned fuses and was unable to unlock it under any tested key or guessed passphrase, then the card was returned to its original device and confirmed to boot and unlock automatically across independent cold boots.

Each device also includes a PIN lock protected by a memory hard key derivation function with a persisted, increasing lockout delay, and an emergency data destruction command that wipes chat history on both paired devices at once, gated by an exact confirmation phrase to prevent accidental triggering.

The main application listener binds specifically to the device's mesh network address rather than all available interfaces, a real gap found and fixed during review and confirmed with a live cross device connectivity test. Each device runs its application as an unprivileged user under a hardened systemd service definition, with sandboxing directives applied deliberately and a small number of exclusions documented directly in the service files where a genuine runtime dependency required them. Privilege elevation available to the application is scoped to exactly the commands it uses, verified against the operating system's own privilege query tooling.

This project has not received a paid, professional security audit, and the custom application protocol has not had formal adversarial cryptographic review. It also depends on Tailscale's coordination infrastructure for mesh identity even with a self hosted relay, and does not include a verified or signed boot chain or a certified hardware security module. These limitations are stated directly rather than implied away. The system is built to meaningfully raise the cost of casual, opportunistic, and moderately resourced attacks against this specific pair of devices, not to claim resistance to a funded or nation state level adversary.

Outside review from computer science, information technology, and security professionals is welcomed, particularly on the application protocol layer described above.
